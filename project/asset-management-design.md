# アセット中央管理の設計案

## 目的と範囲

- エディタとランタイムが同じアセット管理機能を使う。
- アセットブラウザはファイルそのものではなく、登録済みアセットを表示する。
- 外部モデルの取り込みと置き換えを可能にし、シーンの参照を維持する。
- GPUリソースとアセットのCPU側データを分ける。
- 初期段階では独自バイナリ形式を作らず、既存の `.scene`、`.entity`、`.obj`、`.glb`、画像などを利用する。

この文書は移行先の設計案。現在は `AssetRegistry` とモデル用 `AssetManager`、ブラウザの登録一覧、GLB・OBJとPNG・JPEG・BMP・TIFFの取り込み・置き換え、モデルとスプライトのID参照、pakへの登録情報と元データの格納を実装済み。モデルの置き換えは同形式に限るが、画像は対応形式間で変更できる。新規取り込みのGLB内のPNG・JPEG画像も画像アセットとして登録し、モデルからIDで参照する。既存のGLBは同じGLBへ置き換えた際に画像が登録される。置き換え時は画像の内容が一意に一致する場合にIDを維持するが、対応を安全に確定できない場合は拒否する。画像アセット自体は個別に置き換え可能。旧シーンのモデルとスプライトは、一意に登録情報へ対応する旧パスを実行中にIDへ解決する。ボーン・クリップの独立アセット化、曖昧な旧参照の修復、GPUリソースの不要な旧リビジョンの解放などは未実装。

## 現状と課題

- `AssimpModelLoader` は変換したモデルと、GLBのAssimpデータをキャッシュしている。さらに `WindowsEngineResources::modelDataMap` にもモデルデータが保存される。
- GLBのスケルトンとクリップはAssimpのデータに依存している。`ModelData` だけでは現在のGLBアニメーションを再生できない。
- `ModelData` の頂点型は現在シェーダー共有ヘッダーの `MeshVertexData` に依存する。CPUアセットの共通型とGPUへの変換の境界も段階的に整理する。
- 画像は `TextureLoader` などで読み込まれ、描画用ハンドルとして管理される。
- アセットブラウザは `assets` 以下のファイルを走査する。登録情報、再取り込み元、アセット間の依存関係は管理していない。
- シーンは `modelName` や `textureName` にパス文字列を保存するため、移動・改名によって参照が切れる。

## 責務と所有権

```text
                 編集・実行の共通部分
  AssetRegistry ── AssetManager ── AssetFactory / Importer
    登録情報         CPU側の読み込み・保持       外部データの変換
       │                  │
       │                  └── ModelAsset / TextureAsset / ...
       ├── Asset Browser
       └── SceneのAssetId

                 描画側
  RenderAssetCache ── GPUバッファ / テクスチャ / BLAS
```

| 要素 | 責務 | 持たないもの |
| --- | --- | --- |
| AssetRegistry | プロジェクトの登録一覧、ID、種類、表示名、保存場所、依存関係 | 描画用ハンドルや常駐する本体データ |
| AssetManager | IDからアセットを取得し、CPU側の読み込み・キャッシュ・再読み込みを管理 | DirectXのGPUリソース |
| AssetFactory / Importer | GLB・OBJなどを読み込み、アセットデータと依存情報を作る | 登録一覧の永続化、画面操作 |
| RenderAssetCache | アセットIDとリビジョンからGPUリソースを作成・再利用・破棄 | 元ファイルやプロジェクトの登録情報 |
| Asset Browser | Registryの一覧表示、取り込み・置き換え操作、シーンへのドラッグ元 | データの変換や所有 |

初期実装では、`project/engine/assetfactory` にアセット管理のディレクトリを追加し、`EngineAssetsFactory` に含める。`WindowsQuickForgeEngineSystems` はプロジェクト単位の `AssetManager` を所有し、エディタや描画処理には参照を渡す。プロセス全体のシングルトンにはしない。プロジェクトを閉じる際は利用側を先に停止し、描画側の使用終了後にGPUリソースとアセットを破棄する。

## アセットの識別と登録

各アセットはプロジェクト内で一意な `AssetId` を持つ。名前やパスは表示・検索用であり、参照の正体にはしない。IDは作成時に生成して登録情報へ保存し、名前変更・移動・再取り込みでは維持する。新規インポートで同名の別アセットを作るときは別IDを与える。組み込みプリミティブはプロジェクト固有IDと衝突しない、予約された安定IDを使用する。

登録情報の例（形式は初期案）:

```json
{
  "version": 1,
  "assets": [
    {
      "id": "c06ed70f-29d8-49c6-ae00-bc99e0fe1e3f",
      "type": "model",
      "name": "ship",
      "source": "sources/models/ship.glb",
      "dependencies": []
    }
  ]
}
```

初期案では、この登録情報をプロジェクトルートの `asset-registry.json` に保存し、元ファイルをプロジェクト内の `sources/` に保管する。ブラウザには `sources/` の中身を直接表示しない。`.scene`・`.entity` などエディタで作るデータも登録対象にするが、モデルと同じインポート処理を強制しない。

登録情報は起動時に読み込み、変更時に一時ファイル経由で保存する。パスはプロジェクト相対のUTF-8表現とし、プロジェクト外を指すパスや重複IDを拒否する。元データが見つからない場合も登録を消さず、欠落状態と理由を表示する。

## 取り込みと置き換え

1. OSからアセットブラウザにドロップ、またはダイアログで外部ファイルを選択する。
2. Importerが種類を判定し、一時領域で元データと関連ファイルを読み込む。OBJではMTLと画像、GLBでは埋め込み画像・ボーン・クリップを調べる。
3. 変換・検証に成功した後、元データと登録情報を保存し、Managerへ登録する。失敗時はエラーを表示し、既存アセットを変更しない。
4. ブラウザをRegistryの一覧で更新する。シーンへドラッグするとIDを渡す。

置き換えは明示的な `Replace Source...` とし、対象IDを維持する。新しいデータが正常に読み込めた場合のみ置き換え、失敗時は以前のデータを使い続ける。複数ファイルからなるOBJは依存ファイルも確認し、何が欠けているか通知する。OSからのドロップ先と置き換え対象が曖昧な場合は、新規作成か置き換えかをUIで明示する。

GLB内のモデル・画像・スケルトン・クリップには、それぞれの種類と親モデルとの関係を登録する。再取り込み時は元ファイル内の安定した識別情報を優先して対応付けるが、同名・無名・削除・分割・結合などで対応が不明な場合は自動的に別アセットへ付け替えない。欠落を報告し、以前のIDと依存関係を保持してユーザーが修復できるようにする。GLBがAssimp側で統合される場合もあるため、どの情報を維持できるか検証してから変換形式を確定する。

## メモリと描画リソースの更新

`AssetManager` は読み込み済みアセットごとに状態とリビジョンを持つ。CPUデータは型に応じた読み取り専用の共有参照として返し、再取り込みに成功したら新しいデータとリビジョンへ切り替える。取得済み参照は旧データが不要になるまで有効とし、参照がある状態で中身を破壊的に上書きしない。読み込みは初期段階では同期処理とし、非同期化は後の課題とする。

描画側は `(AssetId, revision)` をキーに頂点・インデックスバッファ、テクスチャ、静的BLASなどを再利用する。リビジョン変更を検出したら新しいGPUリソースを作る。旧リソースはGPUの使用完了をフェンスなどで確認してから解放し、描画中に破棄しない。エンティティごとに変形する頂点バッファやBLAS、再生時刻は共有アセットではなく描画・再生の実行時状態として扱う。

初期段階のGLBでは、既存のAssimpベースのボーン・クリップ情報をManagerが所有する読み込み済みモデルの一部として保持する。描画側が `AssimpModelLoader` の別キャッシュへ直接問い合わせるのをやめ、同じ読み込み結果からクリップ一覧とサンプリングを行う。将来、Assimpに依存しないスケルトン・クリップ構造へ置き換える。`ModelData` だけを移してGLB再生が失われる移行はしない。

現行のGLB描画は複数メッシュを結合し、複数マテリアルがあっても基本的に一つのテクスチャを使う。中央管理の導入だけで複数マテリアルに対応したことにはならない。変換仕様の検証時に制限を明示し、対応範囲を決める。

## 公開インターフェースの例

実際の型名やエラー型は実装時に決める。所有期間と失敗を呼び出し元に明示する。

```cpp
// Registry: 表示・参照情報。読み込み済みかどうかには依存しない。
const AssetMetadata* Find(AssetId id) const;
std::vector<AssetMetadata> List(AssetType type) const;

// Manager: CPUデータの読み込みと保持。
Result<AssetHandle<ModelAsset>> LoadModel(AssetId id);
Result<void> Reload(AssetId id);

// Editorの操作。成功時のみ登録内容を更新する。
Result<AssetId> ImportModel(const std::filesystem::path& source);
Result<void> ReplaceModelSource(AssetId id, const std::filesystem::path& source);
```

`AssetHandle` はID・リビジョンと読み取り専用データの共有参照を持つ想定。存在しないID、型違い、ファイル欠落、変換失敗を区別して返す。`ImportModel` と `ReplaceModelSource` はエディタから利用し、ランタイムにファイルダイアログを依存させない。

## 保存とpak

- シーンやEntityには `AssetId` を保存する。再生状態は従来どおりコンポーネントに保存し、頂点バッファなどの実行時ハンドルは保存しない。
- 独自バイナリ形式を作るまでは、ランタイムが使用するために登録情報と必要な元ファイルが必要。現行の `.qfepak` は `project.json` と `assets/` 以下しか格納しないため、`asset-registry.json` と `sources/` を読み込めるよう出力対象・展開検証・ランタイムの参照先を一緒に変更する。
- この暫定段階のpakには元データが含まれる。元データを配布しない要件は、変換済みデータの永続形式と対応ローダーを作った段階で実現する。置き換え前の元データもプロジェクトに残り、現状はpakへ含まれる。
- 既存の `.qfepak` はそのまま読み込める互換経路を維持し、新方式の登録情報がない場合は旧パスを使用する。
- 新しいpakはバージョン2で書き出し、現行ランタイムはバージョン1と2を読み込む。古いバージョン1専用ランタイムではバージョン2のpakを読み込めない。

OBJ取り込みはMTLとその画像をコピーする。MTLの `-o`、`-s`、`-t`、`-mm`、`-clamp` などの標準的なテクスチャ指定オプションと、1行に記述された複数のMTLを扱う。未対応のオプションは取り込みを拒否する。GLBの外部参照テクスチャが取り込み先に存在しない場合も拒否する。

## 段階的な移行

1. RegistryとManagerの基本型を追加し、モデルをパスから登録・取得できるようにする。元ファイルは現状のままでも使用できるようにする。
2. `modelDataMap` と `AssimpModelLoader` のモデルキャッシュを一つの所有元に集約し、GLBクリップの選択・スキニングも同じロード結果を使う。描画用ハンドルは残す。
3. 画像・埋め込み画像・アニメーションクリップを登録し、依存関係を扱う。既存の `TextureLoader` のGPUリソース管理は描画側に残す。
4. アセットブラウザを登録一覧に切り替え、取り込み・置き換えを追加する。シーンの旧パスは読み込み時にRegistryへ解決し、失敗時は欠落として残す。新規保存ではIDを記録し、既存ファイルを自動上書きしない。
5. 登録情報と必要なファイルをpakに含め、エディタとランタイムで同じID解決を使う。変換済み形式と元データを配布しない方式は別途設計する。

各段階で既存の `.scene`、`.entity`、GLBアニメーション、内蔵画像、プリミティブ、シーン切り替え、pak起動を維持する。検証には登録情報の保存・再読込、IDの重複、参照切れ、再取り込み失敗時の復旧、GPUの更新、旧シーンと旧pakの読み込みを含める。

## 今後決めること

- モデル更新時の子アセットの対応付け・競合解決UI。
- 同じ画像を複数モデルで共有する場合の所有権と削除条件。
- シェーダー・スクリプトなど、元ファイルと実行形式の関係がモデルと異なる種類の扱い。
- アセットデータの永続形式、圧縮、プラットフォーム別変換、pakの直接読み込み。
